## What it builds

One row per contact per monthly snapshot, keyed `Contact_Id_YYYYMM`:

- **Book filter**: Contact (003) with `Policy_Effective_Date` and `CreatedDate` on or before the snapshot and no `Cancel_Date` on or before it.
- **Labels**: `Label_60__c` / `Label_90__c` = cancelled within 60/90 days with a preventable voluntary reason (Due to high premium, Replacement of insurance carrier, Insured request - other, App issue / UX, poor customer or claims service). `Censored__c` = cancelled within 60 days for any other reason (non-pay, company, unpreventable); **filter `Censored__c = 0` before training**. `Reason__c` is for evaluation only.
- **Features** (all windowed to dates on or before the snapshot): tenure days and bucket, days since policy effective, estimated days into / to end of a 6-month term, app events 30/90d and recency (`MobileApp_c_..__dll` on Contact `account_id_c__c`; `Account_Id2_c__c` is empty in the Contact lake object even though the Salesforce field is populated), emails sent / opened / clicked 90d, opens 30d, open rate, recency (**Individual Email Results** lake object on `et4ae5_Contact`), Zendesk tickets 90d and recency (on customer number), lifetime savings, telematics discount, policy renewal rate.
- **Audit**: `Max_Feature_Date__c` must never exceed `Snapshot_Date__c`.
- **No payment-derived features**, per the Insurance decision of 2026-10-16.

Branches cross-join each event source to the calendar on a constant key, flag the windows per snapshot, then aggregate by (key, snapshot). App and email event tables are small enough for this (app DMO and 95k contact email rows); if a source grows into the tens of millions, pre-aggregate it to (key, day) first.

## Prerequisites (one-time)

1. **Calendar data stream.** Done 2026-10-20: `Churn_Snapshot_Calendar__dll`, 26 rows, `Snapshot_Key` landed as Number so the transform derives its text key from the date with `date_format(..., 'yyyyMM')`. Add a row each month (re-upload the CSV; the stream is total-replace).
2. **Contact and Account data stream fields.** Added 2026-10-20: `Current_Term_Effective_Date`, `Current_Term_Expiration_Date`, `Last_App_Open_Date`, `Monthly_Safe_Driving_Discount` on the Contact stream, and `Increase_Amount_Dollars`, `Offered_Rate_Change`, `Policy_Renewal_Rate`, `Renewal_Offer_Date` on the Account stream (`Account_00D3h0000068eod__dll`, joined on `AccountId`). The columns exist but are empty until a **full** refresh of each stream runs; the incremental upsert only fills rows modified since the last run.
3. **Renewal offers are point-in-time.** The `Renewal_Offer_c_00D3h0000068eod__dll` lake object (custom object `Renewal_Offer__c`, written by the Account flow `Renewal Offer Capture` since 2026-10-20) holds one row per offer, so the offer joined to each snapshot is the latest one issued in the 60 days before that snapshot. The 7,606 offers back to 2025-10 were backfilled on 2026-10-20 and the stream loaded all of them on its first successful run. Formula fields on the object (`Prior_Rate__c`, `Increase_Percent__c`) arrive null through the CRM connector, so the transform computes the percent from the dollar change and the rate. Verify the lake object name after the data stream is created; the connector suffixes custom objects with the org id.
4. **Known current-value fields.** `Days_To_Renewal__c`, `Days_Since_Renewal_Offer__c`, `Days_Into_Term__c`, `Days_To_Term_End__c`, `Days_Since_Last_App_Open__c`, `Lifetime_Savings__c`, `Telematics_Discount__c`, `Monthly_Safe_Driving_Discount__c`, `Policy_Renewal_Rate__c` and the four `Renewal_Offer_*` columns are read from today's Contact or Account row, so they are only point-in-time for the newest snapshot (the real term columns return null for older snapshots by construction, the others do not). Keep them out of the first training run (exclude in Model Builder) and use them in scoring; they become training features once the AccountHistory stream (offers since 2025-11-14) and Contact field history are joined in. The estimated `Days_*_Est__c` columns stay as the historical stand-in.
4. **Field-name check.** Run `SELECT FIELDS(ALL) FROM MobileApp_c_00D3h0000068eod__dlm LIMIT 1` and a describe of `IndividualEmailResults__dll` and `Zen_Desk_Ticket_Gold__dlm`; the names in the generator were verified 2026-10-16 and will break if a stream is remapped.

## Deploy

**Deployed 2026-10-20 via the API** as `ChurnPITTrainingSet` (the `.nooffers` variant, because the Renewal Offer lake object did not exist yet). To add the offers branch once the `Renewal_Offer__c` data stream exists: delete the transform (or create under a new name) and post `Churn_PIT_Training_Set.api.json`.

**Updating an existing transform:** `PUT /services/data/v64.0/ssot/data-transforms/ChurnPITTrainingSet` with the same body validates and replaces the definition in place (only while its status is ACTIVE or ERROR, not PROCESSING). Run with `POST .../actions/run --body @empty.json` (the CLI needs a body), cancel with `.../actions/cancel`, and read failures from `GET .../run-history?limit=3` (`errorMessage` per run; the detail endpoint only says the run failed).

**After the first run of an API-created transform, add its output lake object to the default data space** (Data Cloud > Data Spaces > default > Add Data Lake Objects). Outputs created through the API are left out of every data space (`dataSpaceInfo: []`), so they are invisible to SOQL and to `ssot/queryv2` until added, even though the run reports its row count. Outputs created in the canvas get the data space automatically.

Option A, API:

```
python3 build_transform_json.py                   # full definition, needs Renewal_Offer_c_00D3h0000068eod__dll
python3 build_transform_json.py --without-offers  # writes the .nooffers variant
sf api request rest "/services/data/v64.0/ssot/data-transforms" -o blueowl-prod -X POST --body @Churn_PIT_Training_Set.api.json
```

What the POST validator enforces (learned 2026-10-20, one error per attempt): formulas are raw SQL (the GET response shows them HTML-escaped, do not post them that way); filter expression types are TEXT / NUMBER / DATETIME / BOOLEAN, never DATE; `outputDataObjects` entries take only label, name, type, category, fields; an aggregate node may not carry an empty `schema`; `pmod` and `greatest` are not available (use floor arithmetic and `case`); `date_format`, `datediff`, `concat`, `coalesce`, `floor`, `to_timestamp`, `INTERVAL n DAY` are fine (`cast(... as timestamp)` and `timestamp()` are not); a formula over a Date column must be wrapped in `to_timestamp()` when its output type is DATETIME, or the *run* fails even though the POST passed; **all inputs must be the same object type**, so this transform reads lake objects only (`__dll`), which is why mobile app and Zendesk come from `MobileApp_c_00D3h0000068eod__dll` and `Zen_Desk_Ticket__dll` rather than the DMOs.

Option B, rebuild in Data Cloud > Data Transforms > New > Batch, using `Churn_PIT_Training_Set.json` as the node-by-node spec. The `ui.nodes` block lists every visual node left to right with its label; each `TRANSFORM` node's `graph` lists the formula steps in order, and `nodes.<id>.parameters.fields[0].formulaExpression` is the formula to paste.

Either way, set the output to a new DLO `Churn_PIT_Training_Set` with `Row_Key__c` as primary key, run once, then run the pre-training checks in `../RETRAIN_point_in_time_labels.md` step 5.

## Scoring variant

Copy the transform, point `LOAD_CAL` at a one-row calendar for the run date (or filter the calendar to the max date), drop the `T_LABELS` label and censoring steps' downstream filter (score everyone), and write to `Churn_PIT_Scoring_Set__dll` with the same columns minus the labels.

## First-run findings (2026-10-20)

- 237,980 rows over 26 snapshots, 11,725 (2024-07) falling to 7,155 (2026-08). The decline is real: distinct contacts billed per month fell from 11,010 in 2024-06 to about 5,900 in 2026, and the old never-cancelled contacts are in force today (term end in the future, bills in the last 60 days). No in-force filter is needed beyond the policy-effective and cancel-date rule.
- Preventable-voluntary 60-day label rate among uncensored rows: 7.7% (2024) trending to 4.4% (2026-08). Shorter tenure churns more in every snapshot (under 6 months 7.7%, 2+ years 5.7%), the opposite of the old training set.
- Leakage audit: 0 rows with a feature date after the snapshot.
- Censored rows are 43% non-pay, 10% company cancel, the rest unpreventable, as designed.
- **Source coverage is uneven.** Individual Email Results holds 17.5k contact sends in 2022, 23k in 2023, but only 5.2k in 2024 and 3.7k in 2025, then 46.7k in 2026; the email features are near-empty for 2024 to 2025 snapshots. Zendesk tickets start in 2025. App events cover 2021 to today (2.18M rows, 57k accounts) once the join key is right.
- First run had zero app events on every row because the join used `Account_Id2_c__c`, which is empty in `Contact__dll`; fixed to `account_id_c__c`.

each to a DMO (Data Lake Objects > object > Map Fields > new custom DMO) before training.

Rule learned the hard way: before adding any Contact field as a feature, group the training set by
its value and year and look at the label rate. A populated value with a ~0% label rate means the
field is only written for customers who are still around.
